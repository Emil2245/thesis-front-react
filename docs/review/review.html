1 · Scope & coverage

The frontend is a React 19 + TypeScript SPA (Vite 8), styled with shadcn/ui 4 on Tailwind 4, using TanStack Query for server state and Zustand for client state, with Vitest + RTL + MSW for unit tests and Playwright + axe-core for E2E and accessibility. Fifteen plans partition the work with hard ordering rules so any plan can be executed from cold context.

2 · The architectural decisions that govern the whole codebase

Any plan executor should know these three before writing a line — they are what makes an implementation that looks right actually match the thesis’s dependent variables.

ADR 9

No calc engine in the client

Every cost, subtotal, HM, CD, CI and CT is computed server-side. RNF-04’s “cálculo en tiempo real” means no page reload, cell-commit granularity: commit a cell → PATCH → repaint from the DTO, with an optimistic pendiente state that shows no guessed number.

Rationale: the thesis’s headline dependent variable is exactitud_calculo = 0% deviation against certified reference cases. A parallel TS implementation would put that at risk for cosmetic gain. Plan 015 mechanises the guard as a CI grep for toFixed/parseFloat outside src/lib/decimal.ts.

API contract §1

Money travels as decimal strings

Money and percentages are branded Decimal strings ("61.390000"), never number. Percentages travel as fractions ("0.1800" = 18 %). Plan 002 brands the type; plan 004 supplies display-only formatters. Never parse to number and send it back.

Rationale: JS number loses precision at the tail digits SERCOP tolerances depend on.

Codebase design §8

One seam with the backend

src/api/ is the only place that knows HTTP exists. No src/features/** file imports axios or builds a URL. DTOs are hand-transcribed from Apéndice B until the Quarkus backend publishes OpenAPI — at which point openapi-typescript replaces the transcription and DTO drift becomes a compile error.

Rationale: keeps HTTP concerns testable at one MSW seam and future-proofs against the still-unbuilt backend.

Design §5.3

Version selector via ?v= (open decision, closed)

Version was open in design/02 §5.3. Resolved to a search param rather than nested routes because TC-P43-02 already assumed it, and it lets any budget/cronograma/export page share one URL scheme without touching the route table.

4 · Gaps & risks flagged (not papered over)

Six items were surfaced during planning. Each is on the record with the plan that bridges it. None is a blocker for v1.1; each is a candidate for the tutor to flag back to the spec owners.

  1. No openapi-typescript source yet. The single seam plus DTO-drift-as-compile-error guarantees depend on OpenAPI, which the still-unbuilt Quarkus backend must publish. Plan 002 bridges with a hand-transcribed Apéndice B and a documented migration path. Until the swap, FE↔BE drift is caught by nothing except the backend’s own API tests.
  2. Firmantes (P-08 / S-11) has no requirements source. Firmante exists in the data model, but v1.1 §2 assigns it neither screen nor process. Plan 007 builds the proposal (a tab in S-09) and isolates it.
  3. No CSV template spec. P-15 / S-16 step ① says “descargar la plantilla del tipo”, but no document defines the columns. Plan 008 derives them from InsumoCrearRequest and flags it.
  4. No preview endpoint for exports. design/03 P-37 step 3 requires a preview; 07 §8 only offers streaming download. Plan 013 previews PDFs from the downloaded blob and shows a summary card for xlsx — at the cost of a second generation round-trip.
  5. Pinned frontend versions were ~1 month stale. 02-shadcn-components.md §0.1 was researched June 2026. Plan 001 installs by major line and writes plans/RESOLVED-VERSIONS.md for reconciliation.
  6. No per-rubro discount preview endpoint (unlike the global discount, which has one — 07 §3). Plan 010 shows before/after values rather than fabricating a preview client-side.
Note on the RESOLVED-VERSIONS diff. pnpm supersedes npm and oxlint supersedes ESLint relative to the pinned spec. Five packages drifted a patch/minor within the same major line (shadcn CLI 4.10 → 4.14, radix-ui 1.5 → 1.6.5, tailwindcss 4.3.0 → 4.3.3, TanStack Query 5.101.0 → 5.101.4, lucide-react 1.17 → 1.25). Consistent with plan 001’s install-by-major-line policy — worth spec-owner sign-off.

Considered and rejected (recorded so they are not re-audited)

  • Client-side document generation (ExcelJS / react-pdf). Rejected: ADR 4 / RNF-03 keep SERCOP-format authority server-side.
  • Client-side calc preview for “snappier” totals. Rejected: ADR 9. The most likely well-intentioned regression, so guarded in CI.
  • Next.js. Rejected upstream: auth-gated internal app, no SEO need, static Cloudflare Pages deploy.
  • Commercial data-grid / Gantt (AG Grid Enterprise, MUI X Pro, SheetJS Pro). Rejected on licensing.
  • Decimal arithmetic library (decimal.js, big.js). Rejected: the client performs no arithmetic; installing one would only enable what ADR 9 forbids.
  • Per-node query keys for the budget tree. Rejected: a single cache key lets whole-tree mutation responses repaint write-through totals atomically.
  • Manual activity CRUD in the cronograma. Rejected: activities are auto-imported 1:1 from budget items — that mechanism is RNF-02’s 100 % linkage guarantee.
  • Jest / Enzyme / Cypress. Rejected upstream (quality/01 §B1, §B2, §B4).

5 · Meeting talking points

  1. Completeness argument. P-01…P-44 and S-01…S-44 are each covered exactly once by the fifteen plans (§1). This is the “whole frontend” claim on which the thesis rests.
  2. Load-bearing architectural constraint. ADR 9 — no client calc engine — is the single decision that keeps exactitud_calculo = 0 % defensible; it is enforced by a CI grep, not by convention alone.
  3. Traceability isn’t decorative. Every plan cites P/S/TC/RNF/ADR/US identifiers; the plans and the thesis stay bidirectionally linkable when the spec repo changes.
  4. Honesty about spec debt. Six unresolved items (§4) are surfaced with the bridging plan named, not hidden behind assumptions. Two of them (openapi-typescript source; firmantes requirements) are appropriate to escalate to the spec owners.
  5. Deferred until the backend exists. The DTO seam and the export preview both improve materially the day the Quarkus service publishes OpenAPI and an export-preview endpoint — plans 002 and 013 already describe the one-file migration.
